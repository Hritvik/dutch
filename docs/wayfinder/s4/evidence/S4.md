# S4 evidence — Corrections, Settlements, and Activity

Status: backend and mobile correction, settlement, and Activity implemented with tests and Android device evidence
Agent: opencode/dutch-agent
Date: 2026-11-01

## Implemented

- **Expense correction** (`ExpenseCorrection`, `ExpenseHistory`): a correction must
  keep the same expense id, group, and currency and must advance exactly one revision.
  It carries one exact reversal per original entry plus the replacement revision's
  entries. `ExpenseHistory` permits at most one correction per revision and keeps the
  full correction evidence.
- **Settlement** (`Settlement`, `SettlementAllocation`, `SettlementVoid`,
  `SettlementHistory`): the parent owns a non-empty, uniquely scoped allocation set
  whose amounts sum exactly to the settlement total and match the parent payer/payee
  and currency. `settle all` is the same parent record with multiple scopes. A void is
  an immutable parent action that exactly reverses every active allocation and can run
  only once.
- **Activity** (`ActivityEntry`, `ActivityLog`): append-only, duplicate-id-safe
  evidence with a closed detail whitelist. Contact-identifier values are rejected, and
  a null actor represents Former member. Creation, correction, deletion, restoration,
  settlement, and membership actions are modeled.
- **Persistence** (`V7`, `V8`): correction, reversal, settlement, void, and Activity
  tables with the evidence/immutability constraints; `JdbcExpenseCorrectionRepository`
  appends the replacement revision, reversal entries (linked to their original entry
  ids in `entry_reversal_link`), correction row, and rebuilt projection; `JdbcSettlementRepository` saves and voids a parent settlement;
  `JdbcActivityRepository` appends and reads scoped Activity.
- **Correction HTTP** (`CorrectionService`, `CorrectionController`): `POST
  /api/v1/groups/{groupId}/expenses/{expenseId}/corrections` takes an
  `Idempotency-Key` and `If-Match` revision, requires an Expense-creating role, builds
  the replacement through the shared `ExpenseCommandFactory`, appends Activity evidence
  with from/to revision detail, and returns the new revision. A reply is scoped to
  actor + command + key and stores the correction result; a retry replays that result
  even though the resource revision moved, and a different payload under the same key
  is `idempotency_conflict`. A stale `If-Match` is `stale_version` without writing.
- **Activity read** (`ActivityService`, `ActivityController`): `GET
  /api/v1/groups/{groupId}/activity` is member-readable, returns the group scope in
  occurrence order, caps the page at 500 entries, omits a null actor (Former member)
  from JSON, and carries no contact identifiers. Free-text details are scanned for
  e-mail/phone substrings, not only exact values. Expense creation now appends
  `EXPENSE_CREATED`, so Activity covers the full expense lifecycle.
- **Expense read** (`ExpenseService.read`, `GET .../expenses/{expenseId}`): returns the
  latest revision to any member who can read the group. The mobile stale-correction
  path uses it to refresh the source revision before re-review, so a stale draft can
  actually be resubmitted.
- **Settlement HTTP** (`SettlementService`, `SettlementController`): `POST
  /api/v1/groups/{groupId}/settlements` records one parent payment with an
  `Idempotency-Key`, defaults the allocation to the group scope, accepts explicit
  group/currency allocations only, and rejects duplicate or foreign scopes. `POST
  /api/v1/groups/{groupId}/settlements/{settlementId}/void` voids once and returns 409
  for a second void. Both commands append Activity evidence and replay their stored
  result for the same key; a changed payload conflicts.
- **Settlement balance application**: each allocation appends a `SETTLEMENT` entry
  from payee to payer (and a `SETTLEMENT_VOID` entry from payer to payee), bumps the
  financial stream version, and rebuilds that stream's projection. Settlements
  therefore reduce the payer's debit immediately and a void restores it.

- **Mobile** (`apps/mobile`):
  - `corrections-client`, `settlements-client`, and `activity-client` parse the closed
    contract shapes, surface `stale_version`/`conflict`/`idempotency_conflict`, and
    send the command identity headers.
  - `drafts.ts` models the Local Draft lifecycle: review before submit, a key frozen on
    the first send, editable validation failure, and `staleNeedsReview` that keeps the
    amount/description, refreshes the source revision, and drops the old key.
  - The expense result screen offers a correction review with the Group/currency scope
    and the before/after total and viewer share, then confirms the exact replacement.
    A stale reply keeps the draft visible and offers "Review latest".
  - The Group screen shows Record settlement and a recent Activity feed with
    privacy-safe details; the settlement screen reviews payer, payee, amount, and scope
    before submit and supports one-shot void with a confirm step.

- Ledger: 141 tests, 0 failures. New coverage:
  - reversal entries cancel the original entries exactly,
  - a correction cannot change identity/group/currency or skip a revision,
  - a history advances and retains every correction,
  - a multi-scope settlement is parent-owned and immutable,
  - allocations must sum to the total and match the parent,
  - a void reverses every allocation once and rejects a second void,
  - Activity keeps creation/correction/deletion evidence, rejects duplicates, and
    rejects contact identifiers,
  - the correction repository appends revision/reversal/replacement rows, links each
    reversal to its original entry, and rebuilds the projection,
  - the settlement repository rejects an unbalanced raw allocation set at commit and
    rejects a parent total rewrite,
  - the Activity repository round-trips details and rejects duplicate/mutated rows,
  - a correction returns the next revision and records privacy-safe Activity,
  - a stale correction is rejected without writing and a malformed `If-Match` is 400,
  - the same correction key replays the stored result and a changed payload conflicts,
  - a non-member cannot correct or read Activity,
  - a settlement records Active evidence, applies its entries, and voids once,
  - settlement allocation scopes must belong to the group and be unique,
  - a settlement key replays its result and a changed payload conflicts,
  - a non-member cannot record a settlement,
  - a correction with missing `Idempotency-Key`/`If-Match` is 400 and a cross-group
    correction is 404,
  - a same-key void replays the accepted void instead of conflicting,
  - Expense creation records `EXPENSE_CREATED` exactly once per command, a
    contact-looking description neither fails the Expense nor enters Activity, a
    member reads the latest revision after a correction, and a non-member read is 404.
- Contract: the Ledger OpenAPI publishes the Expense read and settlement commands;
  `npm test` passes 13 contract tests.
- Mobile: 60 tests, 0 failures; `npm run typecheck` and `npm run lint` pass. New
  coverage: correction/settlement/activity parsing and headers, stale surfacing, and
  the draft transitions (review gate, key reuse, stale preservation, terminal states,
  largest-remainder equal shares, retry key retention), the Expense read client, and
  Activity HTTP errors and null-actor compatibility.

`Medium_Phone_API_36.0` with `EXPO_PUBLIC_DEV_SESSION=1` and the mock API on
`http://10.0.2.2:4010`:

```bash

maestro --device emulator-5554 test apps/mobile/.maestro/correction-stale.yaml
```

- `correction.yaml`: create "Dinner" for 100.00 INR, open the correction review

  "Correction recorded at version 2." → `android-correction-review.png`,

  attempt; the message keeps the draft and "Draft kept: 999.00 INR" remains, "Review
  latest" refreshes the source revision, and the retry records revision 2 →
  `android-correction-stale.png`, `android-correction-recovered.png`.
- `settlement.yaml`: review the "Flat 12 · INR" scope, confirm 50.00 INR, see the
  recorded state, void it with a confirm step, and read "Settlement recorded" then
  "Settlement voided" in Activity → `android-settlement-review.png`,
  `android-settlement-result.png`, `android-settlement-voided.png`,
  `android-s4-activity.png`.

The flows run against the local mock API, so they prove the client contract, review
states, and Local Draft behavior, not the live Ledger.

## Not yet implemented

- HTTP commands for delete/restore.
- The mobile review screen showing scope and before/after consequences before submit,
  and Local Draft preservation on a stale correction.
- Settlement balance application, simplified-plan recomputation, and Activity
  projections.
- Settlement HTTP applies exactly this Group's scope. The cross-group `Settle all`
  command, ordered multi-stream locking, and direct-pair settlement scopes remain
  later work; the contract is narrowed accordingly. Delete/restore remain
  unimplemented at HTTP.
- No Expense list endpoint exists yet, and the correction UI supports a single-payer
  expense; a durable list and multi-payer correction remain an S3 follow-up.
- Local Drafts live in component/application memory only; SQLite persistence and the
  submission-uncertain retry state remain later work. Correction, settlement, and void
  retries keep their key and timestamp across ambiguous failures, but the draft is not
  durable across app restart.
- Concurrent correction/settlement retries are covered by the group lock and the
  durable key, but no load/race test drives two simultaneous commands.

## Residual findings

- Reversal entries currently carry the replacement revision; `entry_reversal_link`
  exists but is not yet populated with the original entry id.
- `Settlement` scope ids are validated as non-blank strings; the repository parses
  group scopes to derive the group and direct scopes to create a direct-pair stream.
  A shared canonical scope parser belongs with the persistence contract.
- The mock API injects `stale_version` on the first 999.00 correction as deterministic
  device test scaffolding; it is not production behavior.
- The immutable `expense` anchor row still carries revision-1 descriptive columns
  (`current_revision`, description, total). Every read resolves `expense_revision`, so
  they are unused legacy evidence; a later migration should drop the duplicates.
- Reversal-to-original links are paired positionally from the deterministic entry
  order; pairing by debtor/creditor is a later hardening step.
- A development database that applied the intermediate V7 (before 65c2e60) must be
  recreated or repaired; the pre-integration schema was never released.
- Activity retention, pagination, and projection rules are later work.
