# S3 evidence — Expenses, entries, and balances

Status: money, allocation, entries, projections, persistence, idempotent HTTP creation, and the mobile composer/result are implemented; correction/stale-edit hardening pending
Agent: opencode/dutch-agent
Date: 2026-11-01

## Implemented

- **Money** (`services/ledger/src/main/java/com/dutch/ledger/expense`): exact signed
  minor units plus an ISO currency, bounded so percentage multiplication stays inside
  `long`. No floating point.
- **Allocation**: equal, exact, and integer-basis-point percentage splits. Percentage
  input must total 10,000; equal and percentage remainders use the largest-remainder
  rule with the stored participant order as the deterministic tie-break. Every
  allocation validates unique positive shares that sum exactly to the total.
- **Expense**: an immutable revision with one or more payer contributions and a
  complete participant share snapshot. Payer contributions and shares must each sum
  exactly to the total. Net positions are contribution minus share; deterministic
  largest-debtor/largest-creditor matching produces immutable Obligation Entries with
  ties broken by Member ID.
- **Balances**: `BalanceProjection` folds entries per currency; the
  `SimplifiedSettlementPlan` derives at most member-count-minus-one transfers without
  rewriting positions.
- **Schema** (`V5`): financial streams, expenses, revisions, payer contributions,
  participant shares, obligation entries, and balance projections, with deferred
  triggers requiring contributions/shares to equal the revision total and entries to
  match each member's contribution-minus-share position at commit.
- **Persistence**: `JdbcExpenseRepository` writes the revision, contributions, shares,
  and entries in one transaction, increments the stream version, and rebuilds the
  member balance projection.
- **HTTP and idempotency** (`V6`): `POST /api/v1/groups/{groupId}/expenses` requires
  `Idempotency-Key`, validates active membership and the group currency, and computes
  the allocation server-side. A durable `(actor, command, key)` outcome stores the
  request hash and response: a retry returns the stored result, and key reuse with a
  different payload is 409 `idempotency_conflict`.
- **Contract**: the Ledger OpenAPI now covers the expense command, its response, the
  `Idempotency-Key` header, and `idempotency_conflict`, with fixtures in the validator.
- **Mobile**: closed expense parsing, a composer for description/amount over the
  active members, and a result screen showing total, exact shares, and who owes whom.

## Device evidence (Android)

`apps/mobile/.maestro/expense.yaml` ran on `Medium_Phone_API_36.0`:

```bash
maestro --device emulator-5554 test apps/mobile/.maestro/expense.yaml
```

The flow passed: sign in, open `Flat 12`, add “Dinner” for `100.00 INR`, create the
expense, and inspect the result: two `50.00 INR` shares, “mem_mem… owes mem_dev… 50.00
INR”, version 1, and the allocation version. Screenshot: `android-expense-result.png`.
It runs against the local mock API, so it proves the client contract and result states,
not the live Ledger.

## Not yet implemented

- Expense correction, delete, restore, reversal links, and revision append; the close
  path currently supports revision 1 only.
- `SERIALIZABLE` retry and an expected stream version; create commands are protected
  by idempotency, but edit/delete race handling is not built.
- Expense list and read endpoints, Activity, and a persisted `group_plan_projection`.
- Direct Expenses, recurring series, settlements, and offline drafts (later slices).
- Device evidence for duplicate/stale retry states; the mock does not emit a 409.

## Residual findings

- The balance projection is rebuilt for the whole stream on every write; switch to
  delta application later.
- The device composer uses one payer (the current member) and an equal split; exact and
  percentage input, payer selection, and review-before-submit are not exposed yet.
- The idempotency outcome stores the response as JSONB; a crash before completion rolls
  back with the expense transaction.
