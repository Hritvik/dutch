# S4 evidence — Corrections, Settlements, and Activity

Status: backend correction, settlement, and Activity commands implemented with tests; mobile review and device evidence pending
Agent: opencode/dutch-agent
Date: 2026-11-01

## Implemented

- **Expense correction** (`ExpenseCorrection`, `ExpenseHistory`): a correction must
  keep the same expense id, group, and currency and must advance exactly one revision.
  It carries one exact reversal per original entry plus the replacement revision's
  entries. `ExpenseHistory` permits at most one correction per revision and keeps the
  full correction evidence.
- **Settlement** (`Settlement`, `SettlementAllocation`, `SettlementVoid`,
  `SettlementHistory`): the parent owns a non-empty, uniquely scoped allocation set
  whose amounts sum exactly to the settlement total and match the parent payer/payee
  and currency. `settle all` is the same parent record with multiple scopes. A void is
  an immutable parent action that exactly reverses every active allocation and can run
  only once.
- **Activity** (`ActivityEntry`, `ActivityLog`): append-only, duplicate-id-safe
  evidence with a closed detail whitelist. Contact-identifier values are rejected, and
  a null actor represents Former member. Creation, correction, deletion, restoration,
  settlement, and membership actions are modeled.
- **Persistence** (`V7`): correction, reversal, settlement, void, and Activity
  tables with the evidence/immutability constraints; `JdbcExpenseCorrectionRepository`
  appends the replacement revision, reversal entries, correction row, and rebuilt
  projection; `JdbcSettlementRepository` saves and voids a parent settlement;
  `JdbcActivityRepository` appends and reads scoped Activity.
- **Correction HTTP** (`CorrectionService`, `CorrectionController`): `POST
  /api/v1/groups/{groupId}/expenses/{expenseId}/corrections` takes an
  `Idempotency-Key` and `If-Match` revision, requires an Expense-creating role, builds
  the replacement through the shared `ExpenseCommandFactory`, appends Activity evidence
  with from/to revision detail, and returns the new revision. A reply is scoped to
  actor + command + key and stores the correction result; a retry replays that result
  even though the resource revision moved, and a different payload under the same key
  is `idempotency_conflict`. A stale `If-Match` is `stale_version` without writing.
- **Activity read** (`ActivityService`, `ActivityController`): `GET
  /api/v1/groups/{groupId}/activity` is member-readable, returns the group scope in
  occurrence order, and carries no contact identifiers.
- **Settlement HTTP** (`SettlementService`, `SettlementController`): `POST
  /api/v1/groups/{groupId}/settlements` records one parent payment with an
  `Idempotency-Key`, defaults the allocation to the group scope, accepts explicit
  group/currency allocations only, and rejects duplicate or foreign scopes. `POST
  /api/v1/groups/{groupId}/settlements/{settlementId}/void` voids once and returns 409
  for a second void. Both commands append Activity evidence and replay their stored
  result for the same key; a changed payload conflicts.
- **Settlement balance application**: each allocation appends a `SETTLEMENT` entry
  from payee to payer (and a `SETTLEMENT_VOID` entry from payer to payee), bumps the
  financial stream version, and rebuilds that stream's projection. Settlements
  therefore reduce the payer's debit immediately and a void restores it.

- Ledger: 135 tests, 0 failures. New coverage:
  - reversal entries cancel the original entries exactly,
  - a correction cannot change identity/group/currency or skip a revision,
  - a history advances and retains every correction,
  - a multi-scope settlement is parent-owned and immutable,
  - allocations must sum to the total and match the parent,
  - a void reverses every allocation once and rejects a second void,
  - Activity keeps creation/correction/deletion evidence, rejects duplicates, and
    rejects contact identifiers,
  - the correction repository appends revision/reversal/replacement rows and rebuilds
    the projection,
  - the settlement repository rejects an unbalanced raw allocation set at commit,
  - the Activity repository round-trips details and rejects duplicate/mutated rows,
  - a correction returns the next revision and records privacy-safe Activity,
  - a stale correction is rejected without writing and a malformed `If-Match` is 400,
  - the same correction key replays the stored result and a changed payload conflicts,
  - a non-member cannot correct or read Activity,
  - a settlement records Active evidence, applies its entries, and voids once,
  - settlement allocation scopes must belong to the group and be unique,
  - a settlement key replays its result and a changed payload conflicts,
  - a non-member cannot record a settlement.

## Not yet implemented

- HTTP commands for delete/restore.
- The mobile review screen showing scope and before/after consequences before submit,
  and Local Draft preservation on a stale correction.
- Settlement balance application, simplified-plan recomputation, and Activity
  projections.
- Settlement commands take the group lock; the cross-group `Settle all` command,
  ordered multi-stream locking, and direct-pair settlement scopes remain later work.
  Delete/restore remain unimplemented at HTTP.

## Residual findings

- Reversal entries currently carry the replacement revision; `entry_reversal_link`
  exists but is not yet populated with the original entry id.
- `Settlement` scope ids are validated as non-blank strings; the repository parses
  group scopes to derive the group and direct scopes to create a direct-pair stream.
  A shared canonical scope parser belongs with the persistence contract.
- Activity retention, pagination, and projection rules are later work.
