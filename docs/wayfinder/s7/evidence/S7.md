# S7 evidence — production readiness and controlled launch

Status: release provenance, an executed restore/projection rehearsal, accessibility
check, CI gates, and the release checklist are in place; production runtime acceptance,
host-build device acceptance, and the real release record remain unexecuted. Dutch ships
inside the Portfolio Super App at launch (ADR 0011), so store submission is not a Dutch
gate.
Agent: opencode/dutch-agent
Date: 2026-11-02

## Implemented

- **Release provenance** (`tools/release-record.mjs`): validates the
  schema-v1 record (artifact digest, source revision, built-at, workflow run URL).
  `infrastructure/provenance/release-record.example.json` validates, and the quality
  workflow validates it on every run.
- **Restore rehearsal**: `infrastructure/local/bin/rehearse-restore.sh` (with a
  superuser fallback and failure cleanup) dumps every
  service database, restores into a sibling database, checks Flyway history and
  failures, compares Ledger entry/outbox counts, and reconciles
  `member_balance_projection` against `obligation_entry`, uses the local superuser
  fallback, and drops restored databases on every exit path. The same procedure is
  executed in `RestoreRehearsalIntegrationTest`: a migrated, populated Ledger is
  dumped with `pg_dump`, restored into a new database, and reconciled (entries,
  outbox, Flyway history, zero projection drift, the expected balance, and a negative
  control that corrupts the restored projection and observes drift).
- **Container images**: one multi-stage `services/Dockerfile` builds any service's
  `bootJar` on Temurin 21, runs it as a non-root user with OCI labels and bounded JVM
  memory; the quality workflow builds all five images in a matrix (no push) with
  BuildKit cache. A tag-triggered `release.yml` publishes them to GHCR with SBOM,
  provenance, and build attestations. A local Docker build was
  attempted but this sandbox's container network cannot reach services.gradle.org, so
  the image build is wired for CI rather than proven on this workstation.
- **Dashboards**: `infrastructure/observability/grafana-dutch.json` panels outbox lag,
  unpublished events, dead letters, failed pushes, and the rate-limited share; the
  foundation check asserts those metrics appear.
- **EAS profiles** (`apps/mobile/eas.json`, phase-2 scaffolding per ADR 0011):
  development (internal build without the
  dev-client dependency), preview (internal), production (auto-increment, store
  submit); the foundation check
  asserts all three exist.
- **Accessibility static gate** (`tools/check-accessibility.mjs`): every `Pressable`
  has a non-empty `accessibilityRole`; every `Image`, `TextInput`, and `Switch` has a
  non-empty label; JSX braces/strings are parsed correctly, and a missing scan root
  fails closed. Enforced in CI.
- **Release checklist and operations** (`docs/operations/release-checklist.md`): gates
  for tests, migrations, restore/outbox, privacy/security, provider acceptance,
  accessibility/performance, store/legal, rollback ownership, and digest promotion.
- **Observability**: Prometheus counters/gauges for outbox lag/DLQ, notification
  deliveries/receipts, and gateway rate limiting, plus
  `infrastructure/observability/dutch-alerts.yaml` for outbox lag, dead letters,
  delivery failures, and the rate-limited share, plus
  `infrastructure/observability/prometheus-scrape.example.yaml` for the three services.
- **Published images**: `v0.1.0` (source `56e32cf`) published all five images to GHCR
  with SBOM, provenance, and build attestations (run `41958283324`, green). Digests are
  recorded per service in `infrastructure/provenance/releases/v0.1.0/` and validated by
  the foundation gate: gateway `sha256:3c5230f8…`, ledger `sha256:03a71fb4…`,
  notification `sha256:b13a2bd3…`, ums `sha256:50411839…`, iam `sha256:78767cc4…`.
- **Supply chain**: `.github/dependabot.yml` covers Gradle, both npm projects, GitHub
  Actions, and the service Dockerfile. The release workflow uses `GITHUB_TOKEN`,
  registry provenance, SBOM, and attestations.
- **CI**: secret scan, release-record validation, accessibility check, migration-order
  test (contiguous per-service Flyway versions), and the existing
  backend/contract/mobile/audit jobs. Dutch does not validate cloud infrastructure:
  provisioning is delegated to a platform provider (ADR 0010).
- **Runtime expectation**: `dutch-managed-production-runtime` in the central
  capability home states the properties Dutch depends on (private networking,
  isolated restorable storage, ordered durable delivery with dead letters, runtime
  secret injection, digest deployment and rollback, alert delivery, separate
  migration credentials). No provider commitment exists yet.
