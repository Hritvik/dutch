## Implemented

- **Gateway routing** (`services/gateway`): a thin `GatewayRoutingFilter` forwards
  `/api/v1/me`, `/api/v1/me/**`, and `/api/v1/ledger/**` to the configured UMS and
  Ledger base URLs. It preserves method, query, body and end-to-end headers, strips
  hop-by-hop and `Connection`-named headers, echoes or regenerates a pinned
  `X-Correlation-ID`, and returns the published error envelope (`unauthorized`,
  `forbidden`, `invalid_request`, `service_unavailable`) through Jackson.
- **Gateway authentication**: `spring-boot-starter-oauth2-resource-server` validates
  bearer tokens against `GATEWAY_IAM_ISSUER_URI`; the security chain requires
  authentication on both routed surfaces and denies everything else. A bearer-token
  test exercises the resource-server path, not only a synthetic principal.
- **Route configuration** (`application.yaml`): `GATEWAY_UMS_BASE_URL`,
  `GATEWAY_LEDGER_BASE_URL`, and `GATEWAY_IAM_ISSUER_URI`.
- **Mobile contract client** (`apps/mobile/src/profile-client.ts`): closed parsing of
  `/api/v1/me/profile-state` and `/api/v1/me`, a positive-integer retry hint capped at
  3600, bearer auth, 409-as-profile-required handling, and fail-closed validation that
  only an `ACTIVE` `PROFILE_READY` Member with a `mem_` id reaches the shell.
- **Mobile shell** (`apps/mobile/app/index.tsx` plus `app-screen.ts`, `app-config.ts`,
  `token.ts`): boot from SecureStore, sign in with S256 PKCE, hold the profile-required
  screen until the authoritative state is ready, retry on the bounded hint, retry
  `/me` while the profile is ready but the Member is not yet committed, return to
  sign-in on 401/403 with a secure wipe, and show retry-plus-sign-out on network or
  contract failures. Ledger availability is derived from the session reducer, never
  from the profile-state response alone.
- **Test harness**: a dev-only session (`NODE_ENV !== 'production'` **and**
  `EXPO_PUBLIC_DEV_SESSION=1`), a loopback mock API, and the Maestro flow.
- **Tests**: gateway 23 (including a real JWKS-decoder context test), mobile 31, contracts 10, infrastructure 2.

## Not yet proven

- The real IAM/UMS journey (external-browser PKCE against a running IAM, a committed UMS
  profile, and the pinned `cor_` correlation) still needs an environment run. `ums/W-18`
  remains the release gate.
- Server-side Ledger authorization is not implemented: the Ledger has no HTTP surface
  yet, so the "Ledger unavailable until the mapping is active" guarantee is currently
  client-side only. It must land with the first Ledger route in S2.
- iOS device evidence is blocked on this workstation: Xcode and `simctl` are absent.
- `EXPO_PUBLIC_IAM_ISSUER` and `EXPO_PUBLIC_DUTCH_API_URL` are not set in a build
  profile yet; the values above were passed on the command line.

## Residual findings

- The router blocks a servlet thread per request; acceptable for the MVP, revisit if
  gateway latency or concurrency becomes a constraint.
- The request timeout bounds response headers, not a slow upstream body stream.
- The mobile client does not refresh tokens yet; a 401 wipes the session and asks the
  person to sign in again.
- No rate limit is applied yet; that belongs to the security slice. The published
  `not_found` and `rate_limited` codes are therefore not yet reachable.
- A slow upstream response body can still pin a servlet thread; the 15s request timeout
  bounds headers only.
- The generated `android/` and `ios/` projects stay untracked and are reproduced by
  `expo prebuild`.
