# S3 evidence — Expenses, entries, and balances

Status: money, allocation, entries, projection, and PostgreSQL persistence implemented; HTTP/mobile and concurrency hardening pending
Agent: opencode/dutch-agent
Date: 2026-11-01

## Implemented

- **Money** (`services/ledger/src/main/java/com/dutch/ledger/expense`): exact signed
  minor units plus an ISO currency, bounded so percentage multiplication stays inside
  `long`. No floating point.
- **Allocation**: equal, exact, and integer-basis-point percentage splits. Percentage
  input must total 10,000; equal and percentage remainders use the largest-remainder
  rule with the stored participant order as the deterministic tie-break. Every
  allocation validates unique positive shares that sum exactly to the total.
- **Expense**: an immutable revision with one or more payer contributions and a
  complete participant share snapshot. Payer contributions and shares must each sum
  exactly to the total; duplicate payers/participants are rejected. Net positions are
  contribution minus share; deterministic largest-debtor/largest-creditor matching
  produces immutable Obligation Entries with ties broken by Member ID.
- **Balances**: `BalanceProjection` folds entries per currency; the
  `SimplifiedSettlementPlan` derives at most member-count-minus-one transfers without
  rewriting positions.
- **Schema** (`V5__create_expense_tables.sql`): `financial_stream`, `expense`,
  `expense_revision`, `payer_contribution`, `participant_share`, `obligation_entry`,
  and `member_balance_projection`, with checks and deferred triggers that require
  contributions and shares to equal the revision total and the entries to match each
  member's contribution-minus-share position at commit.
- **Persistence**: `JdbcExpenseRepository` writes the revision, contributions, shares,
  and entries in one transaction, increments the financial stream version, and
  rebuilds the member balance projection from the stream's entries.

## Not yet implemented

- Expense HTTP commands and reads, and the mobile composer/review/result flow.
- Idempotency keys and the `SERIALIZABLE` retry loop; the repository currently
  assumes a single writer per stream and does not take an expected stream version.
- Expense corrections, reversal links, and revision append (the repository supports
  revision 1 only).
- Persisted `group_plan_projection`; the simplified plan is derived in memory.
- Direct Expenses, recurring series, and settlements (later slices).

## Residual findings

- The balance projection is rebuilt for the whole stream on every write; switch to
  delta application with the same transaction later.
- The deferred trigger proves entries match positions, but the aggregate also validates
  before persistence, so a faulty write path is rejected twice.
- The expense save path has no stream lock or optimistic version precondition yet.
